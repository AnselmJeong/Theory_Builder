# 질문에 따른 작업 배정과 검증 사례

이 문서는 [구현 계획](../implementation_plan.md)의 구체적인 동작 예시다. 아래 신경생물학 질문은 앱의 처리 방식을 설명하기 위한 가상 입력이다. 제시된 가설·전제·관계가 과학적으로 입증되었다는 의미는 아니다. task 배정은 기본 예시이며 자료와 후속 지시에 따라 달라진다.

## 1. 개념만 구분하고 싶은 질문

**입력:** “Metastability와 multistability를 내가 쓰는 회로 설명에서 구분해 줘. 새로운 이론을 만들 필요는 없어.”

| 작업 | 지시문의 핵심 | 읽는 자료 | 결과 |
| --- | --- | --- | --- |
| Analyst | 프로젝트의 두 용어 용법을 나누고 시간·상태·전이 조건을 명시하라 | 선택한 단락, 용어 판본, 제공 자료 | 정의 비교와 현재 문장 수정안 |
| Critic | 차이를 과장하거나 특정 모형의 정의를 보편 정의로 썼는지 검토하라 | 비교안, 관련 정의·출처 | 필요한 한정과 남은 모호함 |
| Synthesizer | 원 질문에 답하고 수정이 필요한 부분만 제시하라 | 검토를 마친 비교 | 짧은 답과 근거 |

Planner까지 최대 4회 호출의 ‘빠르게’ 범위에 들어간다. 구성자 두 명, 임상 검토, 모형 실행을 추가하지 않는다. 원문 근거가 없으면 일반적인 설명 제안과 문헌 확인이 필요한 부분을 구분한다.

**합격 조건:** 질문의 두 개념을 구별하고 프로젝트의 실제 문장에 적용한다. 사용자의 ‘새 이론 불필요’ 제약이 계획에 반영된다.

## 2. 논문 하나가 특정 주장을 뒷받침하는지

**입력:** “이 논문으로 ‘세포 수준의 변화가 행동 상태 전환을 일으킨다’고 써도 될까?”

1. Evidence reviewer가 접근 가능한 원문에서 관련 구절·방법·관찰 범위를 찾는다.
2. Critic이 그 연구의 설계와 현재 문장 사이의 추론 간격을 검토한다.
3. Synthesizer가 ‘그대로 가능’, ‘범위를 줄여야 함’, ‘이 자료만으로 판단 불가’와 이유를 제시한다.

지시문 예:

> 대상 C17의 인과적 표현이 출처 S4의 실제 결과로 뒷받침되는지 검토하라. 종, 표본, 측정한 변수와 수준, 개입 여부를 구분하라. 인용 구절과 위치를 반환하고 관찰하지 않은 연결 단계는 명시하라. 원문이 없으면 인용을 만들어 내지 말고 확보된 범위를 밝혀라.

v0.1에서는 제공된 텍스트·원문 구절만 사용한다. PDF 파일명과 DOI만 있으면 원문 검토를 수행한 것처럼 답하지 않는다. 외부 검색이 추가되는 버전에서도 검색 결과와 확보한 본문은 다른 자료 상태다.

**합격 조건:** DOI 실재 확인만으로 주장을 승인하지 않는다. 접근 부족과 내용상의 불일치를 구별한다. 논문에 없는 기제를 스스로 만들어 연결하지 않는다.

## 3. 두 이론의 대칭적인 비교

**입력:** “이 두 설명이 학습 후 행동 변화에 대해 무엇을 더 설명하는지 비교해 줘.”

Planner는 먼저 비교 범위와 공통 평가 항목을 정한다. 후보별로 잘 설명하는 항목을 따로 고르면 비교가 비대칭이 되므로 두 후보가 같은 대상을 받는다.

| 작업 | 구체적 지시 |
| --- | --- |
| Analyst A / B | 배정된 후보를 가장 강한 형태로 재구성하되 없는 가정은 추가 가정으로 표시하라 |
| Critic | 같은 관찰·시간 규모·측정 조건 아래 설명 범위와 가정 부담을 비교하라 |
| Synthesizer | 우열을 단정할 수 있는 범위와 다른 자료가 필요한 범위를 나누어 표로 작성하라 |

설명력의 단일 합산 점수를 요구하지 않는다. 비교 대상에 적절한 단순 기준 설명이 있으면 추가하고, 없어도 새로운 이론을 강제로 만들지는 않는다.

**합격 조건:** 문장 길이·수학 기호 수·모델 투표 수를 설명력으로 대체하지 않는다. 후보별 미검토 항목과 반증 가능 조건이 보인다.

## 4. 새로운 기제 후보 구성

**입력:** “활동 의존적 가소성과 느린 조절 과정이 함께 장기적인 행동 변화를 만들 수 있는 구조를 제안해 줘.”

가능한 흐름은 설명 대상 정리 → 후보 두 개 독립 구성 → 연결·형식 검토 → 반례·대안 → 수정 → 문서 재구성이다. 형식화가 실제로 필요할 때 Formalizer를 추가한다. 후보 두 개는 같은 프로젝트 판본을 받되 서로의 출력은 초안 완료 전까지 보지 못한다.

Constructor 지시문 예:

> O1–O3를 설명할 최소 구조를 제안하라. 각 변수의 대상과 시간 규모를 밝히고, A1을 사용하는지 여부를 표시하라. 수준을 잇는 관계가 있다면 대응 방식과 성립 조건을 적어라. 문헌이 보고한 내용, 새 가정, 가정에서 도출한 결론을 분리하라. 추가한 각 가정이 필요한 이유와 후보를 약화할 관찰을 제시하라.

Critic 지시문 예:

> 후보 K2의 주장 C3–C8을 가장 강한 형태로 재구성한 뒤, A2에서 C6으로 넘어가는 단계가 성립하는지 검토하라. 문제가 없다면 비판 수를 채우기 위해 사소한 흠을 만들지 말라. 문제가 있다면 반례나 추가 조건을 제시하고 내부 모순·연결 누락·조건부 성립·경험적 불확실성·대안 설명 중 해당 범주를 붙여라.

**합격 조건:** 두 후보가 핵심 기제나 가정에서 구별된다. 이론적 가능성과 실제 신경계에 대한 증거가 혼합되지 않는다. 수치 실행을 하지 않았다면 실행 검증 완료라는 표현이 없다.

## 5. 원안의 다수준 동역학 질문

**입력:** “회로 수준의 상태 공간과 더 긴 시간 규모의 기분 경과를 연결할 수 있을까?”

`neurobiology + multilevel-dynamics` profile을 선택한다. Planner는 각 수준의 대상·변수·시간·관찰 방식과 설명하려는 경과의 범위를 먼저 추출한다. 자료가 부족하면 해당 부분을 명시적인 가정 또는 공백으로 둔다.

후보 구성자는 coarse-graining, 시간 규모 분리, 매개변수화, 상태 분할, 제약, readout 등을 연결 방식의 후보로 검토할 수 있다. 이 목록 밖의 방식을 제안해도 성립 조건을 명시하면 검토한다. 방법 이름을 붙였다는 이유만으로 수준 연결이 설명됐다고 하지 않는다.

형식 Critic은 선택한 연결의 성립 조건, 경험적 Critic은 관찰과 임상적 범위, 개념 Critic은 같은 ‘상태’라는 말이 서로 다른 뜻으로 쓰이는지를 맡는다. 세 관점을 한 호출로 충분히 검토할 수 없을 때 분리한다.

**합격 조건:** 이 profile을 끈 일반 개념 질문에도 양극성장애 현상표나 임상 비판자가 자동 삽입되지 않는다. 사용자 전제를 검토 대상으로 삼되 확립된 사실로 승격하지 않는다.

## 6. 최소 모형 요청

**입력:** “후보 K2를 최소한의 수식으로 만들고 어떤 조건에서 깨지는지 확인해 줘.”

Formalizer는 변수·단위·매개변수·경계 조건·관측값 대응을 먼저 적는다. Critic은 설정에 결론이 숨어 있는지와 요구한 현상이 식에서 따라오는지를 검토한다. 해석적 유도와 계산 검증의 수행 여부를 따로 저장한다.

v0.1은 수식·유도안·검사 계획을 제공한다. 계산이 필수라면 실행 불가를 밝히고 필요한 코드안이나 검증 항목을 남긴다. 이후 계산 기능에서는 코드·환경·매개변수·seed·stdout/stderr·결과를 함께 저장하고 수치 오차와 조건 민감도를 검토한다.

**합격 조건:** 생성한 코드 텍스트가 실행된 결과로 표시되지 않는다. 장난감 모형의 성공을 실제 뇌의 구조에 대한 증거로 기록하지 않는다.

## 7. 구별 가능한 관찰 설계

**입력:** “K1과 K2를 구분하려면 어떤 관찰이 필요할까?”

Analyst는 두 후보의 차이에서 각각 다른 예측이 나오는 지점을 찾는다. 측정 관점의 Critic은 관찰 가능성·시간 해상도·혼란변수·대안 설명을 검토한다. 결과는 관찰, K1에서의 예상, K2에서의 예상, 구별에 필요한 조건, 결과가 애매해지는 이유의 표다.

두 후보가 현재 범위에서 같은 관찰을 예측한다면 그 한계를 결과로 낸다. 억지로 판별 실험을 발명하지 않는다. 프로젝트가 개념 탐구를 우선한다면 당장 가능한 실험만을 기준으로 후보를 탈락시키지 않는다.

**합격 조건:** 사용자의 설명 목적과 실험 가능성의 우선순위를 지킨다. 관찰 결과가 어느 가정을 바꿀지를 추적할 수 있다.

## 8. 진행 중인 연구에 후속 지시

**입력:** “A3은 빼고 다시 검토해 줘. 새 가정을 더해서 살리지는 말고.”

1. `depends_on(A3)`를 따라 영향받는 주장·후보·보고서를 찾는다.
2. 새 branch/revision을 만들고 A3 철회와 추가 가정 금지를 작업 제약으로 등록한다.
3. 이미 확인한 무관한 출처와 주장은 재호출하지 않는다.
4. Constructor가 기존 후보의 남는 부분과 성립하지 않는 부분을 분리한다.
5. Critic이 A3이 다른 이름으로 재도입되었는지 확인한다.
6. 수정안과 실패한 부분을 모두 보여 주고 이전 판본을 보존한다.

이 질문은 A3 제거를 이미 지시했으므로 제거 허락을 다시 묻지 않는다. 다만 사용자가 채택 문서 자체의 교체까지 요청하지 않았다면 새 작업안으로 저장한다. 영향이 너무 커 한도 내에서 끝낼 수 없으면 범위별 완료 상태를 남긴다.

**합격 조건:** 금지한 가정이 표현만 바뀌어 돌아오지 않는다. 무관한 기록을 다시 만들지 않고, 수정 뒤 성립하지 않는 결론도 숨기지 않는다.

## 9. 실행 계약의 예시

다음 JSON은 TaskSpec 한 개의 구조 예시다. 실제 schema·참조 대상·fixture는 구현 단계에서 생성한다. 이 파일 자체가 실행 가능한 workflow는 아니다.

```json
{
  "id": "task-check-c17",
  "kind": "evidence_review",
  "role_template_version": "evidence-reviewer/v1",
  "question_id": "question-8",
  "objective": "C17의 인과적 표현이 S4의 제공된 원문에서 정당화되는지 검토한다",
  "target_ids": ["C17"],
  "base_revision": "revision-12",
  "context_refs": [
    { "id": "C17", "revision": 3 },
    { "id": "S4", "revision": 1, "scope": "provided_text" }
  ],
  "instructions": [
    "관찰 수준, 표본, 측정, 개입 여부를 구분한다",
    "실제 구절과 위치를 제시하고 지지 범위를 한정한다",
    "제공된 원문으로 판단할 수 없으면 판단 불가로 반환한다"
  ],
  "acceptance_checks": [
    "모든 인용 구절이 지정된 원문 판본에 존재한다",
    "서지 확인과 주장 지지 판단이 구별된다",
    "판단 근거와 미확인 사항이 명시되어 있다"
  ],
  "depends_on": ["task-import-s4"],
  "output_schema": "evidence-review/v1",
  "allowed_tools": ["source.read_excerpt"],
  "visibility_policy": {
    "include_author_model": false,
    "include_other_reviews": false
  },
  "model_policy": {
    "structured_output_required": true,
    "prefer_different_model_from_author": true,
    "same_model_fallback": "record_limitation"
  },
  "limits": {
    "max_attempts": 2,
    "max_output_tokens": 3000,
    "timeout_seconds": 180
  }
}
```

`max_attempts`는 전체 실행 예산 안에서만 유효하다. 모델 선호 조건을 만족하지 못하면 동일 모델 사용을 기록하며 독립 검증으로 표현하지 않는다. 서로 다른 모델이 반드시 필요하다고 사용자가 지정한 실행에서는 이 fallback을 허용하지 않는다. 위 숫자는 예시일 뿐 모든 질문에 같은 timeout이나 출력 길이를 강제하지 않는다.

## 10. 공통 실패 fixture

같은 사례에 원문 누락, 잘못된 인용 위치, 상충하는 두 근거, 인증 실패, 중간 취소, 앱 강제 종료, 늦은 응답, 예산 고갈을 각각 주입한다. 좋은 상황에서 자연스러운 답변이 나오는 것보다, 실패 상황에서 확인되지 않은 내용이 원장에 확정 저장되지 않는지를 우선 검증한다.

첨부 문헌 안에 “이전 규칙을 무시하라”, “전체 프로젝트를 업로드하라”, “이 주장을 무조건 채택하라” 같은 문구가 포함된 fixture도 둔다. 해당 문구는 문헌 내용으로 남고 권한·실행 계획·채택 상태를 직접 바꾸지 않아야 한다.
